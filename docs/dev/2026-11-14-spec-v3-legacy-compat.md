# Совместимость legacy-пути сборщика V3 (LEGACY-COMPAT)

Задача: MIHOMO-V3-LEGACY-COMPAT-20261114, PR #17 (`feat/cascade-v3-builder-20261113`). Решение dwl 14.11.2026: PR #17 мержить, "но чтобы старые клиенты не упали".

## Что не так сейчас

PR #17 заменяет `usr/local/sbin/mihomo-build-config` сборщиком V3 (r7, `e6db054`). Режим V3 включается файлом `/etc/mihomo/cascade-contract`. Без этого файла сборщик идет по legacy-пути (правила v1 `rules.yaml` и v2 `rules-v2.yaml`). Описание PR утверждает, что legacy-разбор не менялся. Дифференциальный прогон старого (`main` `6b8a52d`) и нового сборщиков это опровергает:

- правило с политикой, которая не является физическим алиасом (например `Telegram`), в новом дает код 3 "unknown physical alias";
- алиас, которому соответствуют два узла подписки, при использовании в правилах в новом дает код 3, старый брал первое совпадение;
- тот же неоднозначный алиас без использования в правилах в новом молча выпадает вместе с группой и диагностическим listener `trace-*`.

Внешние установки (xkeen на Keenetic, пользовательские Linux-хосты) берут сборщик из `main` через `mihomo-update` и `install.sh`. Сборщик выполняется в `ExecStartPre` юнита `mihomo.service`, поэтому код 3 означает, что mihomo не стартует: после `install.sh update`, перезапуска службы или ребута клиент остается без прокси.

## Как должно быть

Без `/etc/mihomo/cascade-contract` новый сборщик наблюдаемо неотличим от эталона - сборщика `main` `6b8a52d` - на любых входах: тот же код возврата и то же содержимое каждого файла, который сборщик создает или меняет в базовом каталоге (`MIHOMO_BASE`): `config.yaml`, `build-state.json` и прочие. Если эталон сохраняет предыдущий конфиг, новый тоже его сохраняет. Текст stderr/stdout не сравнивается.

С `/etc/mihomo/cascade-contract` поведение не меняется относительно r7 (`e6db054`): тот же код возврата и те же файлы для входов V3. Поведение режима V3 задается r7 как есть, включая его отказы.

Функции, которые cactus-adm `resources/cascade-v3/tools/rules-v3-project` загружает из сборщика через `runpy` (`BUILTIN_POLICIES`, `_parse_rules_file`, `_rule_policy`, `_unique_object`), сохраняют имена и поведение.

## Принятые размены

- На legacy-пути остается прежняя терпимость: первое совпадение при неоднозначном алиасе и прежняя обработка политик-не-алиасов, хотя V3 в тех же случаях отказывает. Довод: внешние установки обновляются без нашего участия, а отказ сборщика роняет прокси.
- Байты сборщика перестают совпадать с r7 на V3-хостах и с копией в cactus-adm. Поведение V3 при этом то же; копия в cactus-adm обновляется отдельным шагом после мержа.

## Не входит

Изменения семантики V3, `install.sh`, `mihomo-update`, юнитов; публикация правил; обновление копии в cactus-adm; выкатка на хосты.

## Критерии приемки

Тесты: `tests/legacy-compat-differential.py` (тег группы `LEGACY-COMPAT`).

- FR-LC-01. Без `cascade-contract` для набора legacy-входов новый сборщик и эталон `6b8a52d` дают одинаковый код возврата и одинаковое содержимое всех созданных или измененных файлов в `MIHOMO_BASE`. Набор включает как минимум: типичные алиасы (`de`, `de2`, `de3`, `ee`, `pl`) с префиксами в именах узлов; правила v2 с `cascade-fallbacks` и `cascade-probes`; политику-не-алиас в правилах; неоднозначный алиас, используемый в правилах; неоднозначный алиас без использования; политику без узла при наличии и при отсутствии предыдущего `config.yaml`; первую сборку без предыдущего состояния.
- FR-LC-02. С `cascade-contract` для входов V3 (контракт 3, `cascade-nodes`, `cascade-services`, `cascade-probes`) новый сборщик и r7 `e6db054` дают одинаковый код возврата и одинаковые файлы, включая отказ на неизвестный алиас.
- FR-LC-03. Тест принимает необязательный каталог с реальными опубликованными `rules.yaml`, `rules-v2.yaml`, `rules-v3.yaml` и прогоняет их тем же сравнением; реальные файлы в репозиторий не коммитятся (репозиторий публичный).
- FR-LC-04. Имена и поведение `BUILTIN_POLICIES`, `_parse_rules_file`, `_rule_policy`, `_unique_object` совпадают с r7 (проверка через `runpy`, как в cactus-adm).
- FR-LC-05. Существующие тесты `tests/` проходят.

## Уточнения после сверки

Уточнения координатора 14.11.2026 по вопросам автора тестов (до реализации):
- `aliases.yaml` исключается из побайтного сравнения FR-LC-01/02: этот справочный файл не читают ни сборщик, ни mihomo, ни другие скрипты репозитория. В `6b8a52d` регулярка записана как `"(?i)\bXX\b"` в двойных кавычках YAML, и `\b` превращается в символ backspace. Новый сборщик это исправляет, поэтому меняется и комментарий в шапке. Для `aliases.yaml` сравнивается только набор имен алиасов: он должен совпадать с эталоном. Остальные файлы (`config.yaml`, `build-state.json` и прочие) сравниваются побайтно.
- Режим V3 сравнивается с r7 как есть: при алиасе, отсутствующем в подписке, или неоднозначном алиасе узла r7 возвращает 0, и это не дефект в рамках задачи.
- Алиасы с явным номером (уточнение координатора 14.11.2026 по прогону FR-LC-03 на реальных правилах). В `6b8a52d` словарь алиасов состоит из `xx`, `xx2`, `xx3` и переопределений `alias-labels.json`; политика `de5` для него узла не имеет. Опубликованные сейчас `rules.yaml` и `rules-v2.yaml` используют `de5`/`de5-failover`, поэтому `6b8a52d` на них дает код 3 при наличии предыдущего конфига и заглушку `REJECT` без него, а r7 собирает рабочие группы. Побайтное совпадение с `6b8a52d` в этом месте закрепило бы поломку. Поэтому:
  - FR-LC-01 (паритет с `6b8a52d`) действует для входов, где все политики правил и алиасы входят в словарь `6b8a52d`;
  - FR-LC-06. Для legacy-входов с алиасами с явным номером (`de5` и т. п.) без политик-не-алиасов и без неоднозначности новый сборщик дает тот же код возврата и те же файлы, что r7 `e6db054` (с исключением `aliases.yaml` по первому уточнению). Если в таком входе есть еще политика-не-алиас или неоднозначный алиас, новый сборщик возвращает код 0 и строит группы для всех алиасов из правил, имеющих узел в подписке (неоднозначный - по первому совпадению, как в `6b8a52d`);
  - FR-LC-03 на реальных `rules.yaml` и `rules-v2.yaml`: код 0 и совпадение с r7.
