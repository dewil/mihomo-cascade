# Находки Андрея по установщику: каталог, права на кэш, место для состояния - ВЫСОКАЯ

Заведено 21.09.2026 по сообщениям Андрея Мосиенко в личке dwl: он ставил `mihomo-cascade` на
чистую Ubuntu как клиент (не каскад) и наткнулся на три вещи подряд. Все три проверены по коду
и по боевым нодам - подтвердились.

## 1. Установщик падает, если нет `/usr/local/sbin`

Симптом дословно:

```
install: cannot create regular file '/usr/local/sbin/mihomo-build-config': No such file or directory
```

`install.sh` кладет четыре скрипта в `/usr/local/sbin` (строки 373-376) без предварительного
`install -d`. Для каталога юнитов и для `/etc/mihomo` он это делает (строки 41, 345-346), а для
`/usr/local/sbin` - нет. На большинстве образов каталог есть, поэтому дефект не виден; на
минимальном образе или в контейнере установка обрывается на середине, уже поставив бинарь и
конфиги.

**Лечение:** `install -d -m 755 /usr/local/sbin` перед установкой скриптов.

## 2. `mihomo` не может создать `cache.db`, и наш парк это скрывает

Симптом дословно:

```
level=warning msg="[CacheFile] can't open cache file: open /etc/mihomo/cache.db: permission denied"
```

Причина: установщик делает `install -d -o root -g mihomo -m 750 /etc/mihomo` (строка 345), то
есть каталог принадлежит `root:mihomo` с правами 750 - процесс под пользователем `mihomo` может
читать и входить, но **не может создавать файлы**. А `mihomo -d /etc/mihomo` (юнит, строка 13)
хранит `cache.db` именно в этом каталоге.

**Почему это не всплыло раньше - и почему это тихий отказ.** На `ru2` и `ru3` предупреждения нет
и `cache.db` на месте: файл создан 30.03 и 23.04.2026, когда каталог был доступен на запись, и
владеет им `mihomo:mihomo`. Сейчас права каталога - 750 `root:mihomo` на обеих нодах, то есть
**записать в существующий файл процесс может, а создать его заново - нет**. Пока файл лежит,
парк выглядит исправным; любая новая нода воспроизводит ошибку Андрея, а пропажа файла на
старой (чистка, перенос, переустановка) превращает исправную ноду в ту же самую.

Тихо это потому, что сообщение имеет уровень `warning`, а не `error`: служба поднимается, туннель
работает, а то, что зависит от кэша - сохранение выбранного узла между перезапусками и
персистентность fake-ip, - молча не работает. Проверка "служба active" отвечает одинаково в обоих
состояниях.

**Обходной путь, которым воспользовался Андрей:** `chown -R mihomo:mihomo /etc/mihomo`. Он
работает, но отдает процессу на запись весь каталог конфигурации - то есть лечит симптом ценой
того, что служба может перезаписать свои же правила и ключи.

## 3. Состоянию не место в `/etc` - предложение Андрея

Дословно: "а лучше cache всякие делать в `/var/lib/mihomo` например".

Это верное решение, а не вкусовое: `/etc` - для конфигурации, изменяемое состояние живет в
`/var/lib` (FHS). У systemd для этого есть `StateDirectory=mihomo` - он сам создает
`/var/lib/mihomo` с нужным владельцем и правами, и каталог конфигурации остается только для
чтения. Тогда пункт 2 закрывается не правами на `/etc/mihomo`, а тем, что писать туда больше
нечего.

Упирается это в то, что `mihomo -d <dir>` задает **один** каталог и для конфигурации, и для
состояния, поэтому развести их надо проверить на факте: либо ключом самого mihomo, если он есть
в нашей версии, либо симлинком `cache.db` в `/var/lib/mihomo`, либо переносом рабочего каталога
целиком с чтением конфигурации по абсолютному пути. Выбор - после проверки, а не на глаз.

## 4. Не дефект, а прием: SOCKS5 в локальную сеть

Андрей настраивал mihomo как прокси для телефонов - Telegram на мобильных умеет socks5 и не
умеет http:

```yaml
allow-lan: true
bind-address: "*"
```

дальше в Telegram - socks5, адрес сервера, порт 7891. Порт у нас уже есть
(`config.base.yaml:5`), по умолчанию стоит `allow-lan: false` и `bind-address: "127.0.0.1"` - и
для каскадной роли это правильный дефолт, менять его не надо.

**Но записывать этот прием в документацию в таком виде нельзя.** `bind-address: "*"` на машине с
публичным адресом открывает SOCKS5 на всех интерфейсах, то есть делает открытый прокси - это и
магнит для злоупотреблений, и нарушение правил почти любого хостера. В рецепте для человека
должно стоять `bind-address` с адресом локальной сети (или ограничение по
`lan-allowed-ips`/фаерволу), а не звездочка. Домашний сервер за NAT - единственный случай, где
звездочка безобидна, и это надо сказать прямо.

## Что сделать

1. `install -d -m 755 /usr/local/sbin` в установщик (пункт 1) - правка в одну строку.
2. Развести конфигурацию и состояние (пункты 2-3): проверить, чем именно, и закрыть предупреждение
   на **новой** ноде, а не на существующей - на существующей его не видно по причине выше.
3. Тест установки на образе без `/usr/local/sbin` и без предсозданного `cache.db` - иначе оба
   дефекта вернутся незамеченными.
4. В README - раздел про клиентское использование на Linux (mihomo как прокси для локальной сети)
   с безопасным рецептом из пункта 4.

## Почему высокая

Пункты 1 и 2 ломают установку на чистой машине - то есть ровно тот сценарий, которым к нам
приходит новый человек, и единственный, который мы не проверяем: свои ноды мы обновляем, а не
устанавливаем с нуля. Андрей нашел оба за один вечер.

Пункт 3 (полный переезд рабочего каталога и `geoip.metadb` в `/var/lib`) **не сделан осознанно**

**Карточка остается открытой до проверки на живой ноде.** Тестом это не покрывается, и спека
называет остаток прямо: что старый `cache.db` заменился ссылкой, что новый файл появился в
`/var/lib/mihomo` с владельцем `mihomo:mihomo`, и что предупреждение `[CacheFile] can't open
cache file` пропало из журнала. mihomo стоит только на `ru`, `ru2`, `ru3` - все три клиентские,
рестарт рвет активные соединения через каскад, поэтому окно выбирает dwl.

Что уже проверено без прода: `ln -sfnT` поверх обычного файла ставит ссылку, запись через
висячую ссылку создает цель, повтор идемпотентен, поверх каталога `-T` отказывает; на всех трех
нодах `ln` в `/usr/bin/ln`, systemd 249 и 255, `/var/lib/mihomo` не существует.
