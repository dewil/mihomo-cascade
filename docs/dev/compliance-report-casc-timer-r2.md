**Три исходные находки исправлены. Штатная миграция cron → timer закрыта с учётом обновлённой спеки.** Нашёл две новые неточности: ложное обещание защиты ручного запуска в README и неправильное форматирование одного класса нестандартных расписаний. Само штатное расписание они не ломают.

Проверен `370951f..d02e34c`. Файлы не менял, боевые машины не трогал.

**Вердикт по каждой находке**

1. **Закрыто.** Создание каталога, копирование каждого юнита и удаление cron теперь имеют собственные `if ! …; return 1`: [install.sh:41](/data/git/mihomo-cascade/install.sh:41), [install.sh:47](/data/git/mihomo-cascade/install.sh:47), [install.sh:131](/data/git/mihomo-cascade/install.sh:131).

   Подтвердил отдельно отказ каждой из трёх команд `install` и отказ `rm` подстановками в памяти. Во всех случаях код 1, успеха нет; при ошибках `install` вызовы `systemctl` не начинаются. Контекст `|| exit $?` больше не мешает этим проверкам.

2. **Закрыто, но появилось новое — неверное обещание защиты ручного запуска.**  
   [ExecStart:24](/data/git/mihomo-cascade/etc/systemd/system/mihomo-refresh.service:24) берёт тот же `/run/mihomo-refresh.lock`, что старый cron. Поэтому новые запуски таймера и старые cron-команды взаимно исключаются, включая cron-процесс, переживший удаление файла расписания.

   Окно двух планировщиков осталось, но теперь оно означает дополнительные **последовательные** прогоны, а не гонку за временные файлы. Это прямо принято в [уточнении спеки:76](/data/git/mihomo-cascade/docs/dev/2026-09-08-spec-casc-timer.md:76).

   **Новая неточность, средняя важность:** [README:109](/data/git/mihomo-cascade/README.md:109) утверждает, что под лок попадает ручной `mihomo-refresh`. Это неверно: лок находится снаружи скрипта, только в `ExecStart`; сам скрипт его не берёт.

   Шаги на стенде: запустить длительный refresh через сервис, затем вызвать `mihomo-refresh` напрямую. Ручной экземпляр начнёт работу параллельно. Само поведение существовало раньше; новая ошибка — утверждение, что оно теперь защищено. Для исправления обещания достаточно поправить документацию, менять контракт ручного запуска необязательно.

3. **Закрыто, но появилось новое — слишком широкий шаблон форматирования.**  
   Значения читаются из установленного файла на [install.sh:93](/data/git/mihomo-cascade/install.sh:93), вывод собирается на [install.sh:138](/data/git/mihomo-cascade/install.sh:138). Константы расписания больше нет.

   **Новая ошибка, низкая важность:** шаблон на [install.sh:98](/data/git/mihomo-cascade/install.sh:98) принимает любой хвост после первой цифры, а не только целое число.

   Воспроизведение: установить на стенде допустимое `OnCalendar=*:0/2:30`. Вывод будет **«раз в 2:30 мин»**, хотя смысл — каждая чётная минута на 30-й секунде. Подтвердил форматирование в памяти и допустимость выражения через `systemd-analyze calendar`. Нужна строгая проверка формы `*:0/число`; остальные выражения должны идти в существующий буквальный вывод. Штатное `*:0/2` работает правильно.

**Проверка `flock` и таймаута**

- **Занятый лок действительно даёт штатный пропуск.** Проверил настоящим `/usr/bin/flock`, используя анонимный объект в памяти вместо файла `/run`: свободный лок → команда выполнена, код 0; занятый → команда не выполнена, код 0. Для `Type=oneshot` такой выход успешен, а не `failed`. `-E 0` не скрывает ненулевой код самого refresh. Это соответствует [документации util-linux](https://raw.githubusercontent.com/util-linux/util-linux/v2.39.3/sys-utils/flock.1.adoc).
- **Ожидания освобождения лока нет:** `-n` запрещает ожидание. `TimeoutStartSec=300` охватывает весь `ExecStart`, включая flock и дочерний refresh.
- Комментарий [сервиса:27](/data/git/mihomo-cascade/etc/systemd/system/mihomo-refresh.service:27) «не удержит лок дольше пяти минут» слишком категоричен. На 300-й секунде начинается остановка; принудительное завершение может потребовать дополнительного `TimeoutStopSec`. Это неточность комментария, не новая поломка таймаута. [Правила остановки systemd](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.service.xml).
- **Без `/usr/bin/flock`** запуск сервиса закончится `203/EXEC`. Проверки enabled/active самого таймера этого не обнаружат, установщик может сообщить успех. Проверки наличия исполняемых зависимостей здесь нет. Это эксплуатационное предусловие; flock уже требовался старому cron, а его использование теперь явно предписано спекой.
- **Ручному прямому запуску лок не мешает:** он отвечает сразу, но и взаимного исключения с таймером не получает. Также новый лок не охватывает `ExecStartPre` другого сервиса и не может задним числом защитить уже работающий экземпляр старой версии без flock.

**Чтение расписания**

Для обычного нестандартного выражения вроде `daily` вывод корректно становится «по расписанию daily». Ошибка касается распознавания расширений формы `*:0/N`, описанного выше.

Без `RandomizedDelaySec` хвост о случайной задержке исчезает. Это соответствует значению systemd по умолчанию — нулевой задержке. Шаг при этом не проверяет соблюдение штатного требования `59s`; его проверяют тесты поставляемого юнита.

Drop-in действительно не учитывается. **При явно принятом условии «drop-in нет» это допустимый размен, повторно находку не открываю.** Но вывод описывает основной файл, а не эффективную конфигурацию менеджера. Если drop-in появится, например уберёт задержку или добавит `Persistent=true`, сообщение может стать неверным. Повторная установка такие файлы не удаляет и это расхождение не исправляет.

**Состояния при прерывании шага scheduler**

Ниже «cron сохранён» означает сохранение файла, а не гарантию наличия работающего демона cron.

| Место прерывания | Что остаётся |
|---|---|
| Проверка `systemctl`, создание каталога | Старый механизм не изменён; возможно создан каталог. |
| Копирование service или timer | Возможна неполная пара или частично записанный файл. Перезагрузки конфигурации менеджера ещё не было; cron сохранён. |
| `daemon-reload` | Новые файлы на диске; существующий таймер мог продолжать работать. При ошибке нельзя утверждать, что он обязательно выключен. |
| `enable --now` | Возможен частичный результат: включена автозагрузка, но запуск не завершён. Cron сохранён. |
| `restart` | Таймер мог остаться активным либо остановиться перед неудачным стартом. Cron сохранён. |
| `is-enabled`, `is-active` | Отката нет. Возможны активный таймер плюс cron или только прежний механизм. |
| Чтение расписания | При ошибке после успешных проверок остаются активный таймер и cron. Это новый явный путь отказа после активации. |
| Удаление cron | До успешного удаления — оба механизма; после — таймер и, возможно, ещё выполняющаяся старая cron-команда под общим локом. |
| Печать результата | Планировщик уже настроен; потеря вывода состояние не меняет. |

**Нового состояния, из которого нельзя выйти повторной успешной установкой, не нашёл.** Повтор перезаписывает оба юнита, перечитывает их, включает/перезапускает таймер и повторяет удаление cron. Постоянную внешнюю причину — read-only диск, запрет удаления, отсутствующий flock, конфликтующий drop-in — повтор сам не устраняет.

Для уже установленного таймера без cron неудачный `restart` может оставить обновление остановленным до успешного повтора. Это существующий риск порядка, не следствие новых проверок файлов.

В полной установке после scheduler по-прежнему идёт [start/restart mihomo](/data/git/mihomo-cascade/install.sh:372). Его отказ не откатывает готовый планировщик. Немедленная сборка через `ExecStartPre` и возможное пересечение с refresh остались прежними.

**Тесты и их различающая способность**

Полные 69 проверок и `stub-policy.sh` **не подтверждены запуском в этой среде**: предварительный `mktemp` снова получил `Read-only file system`. После этого тесты не запускал, поскольку они продолжают выполнение с пустым `SB`. `bash -n` прошёл. Вместо полного прогона выполнены описанные выше проверки в памяти.

Среди новых тестов есть реальные пробелы:

- **`installfail` ломает сразу первый `install -d`.** Поэтому сценарий на [tests/scheduler-install.sh:236](/data/git/mihomo-cascade/tests/scheduler-install.sh:236) останется зелёным, если убрать проверки ошибок копирования отдельных юнитов, сохранив проверку создания каталога. Это конкретный случай одинакового результата исправного и сломанного кода. Сейчас сами проверки копирования реализованы правильно.
- Тест расписания [на строке 302](/data/git/mihomo-cascade/tests/scheduler-install.sh:302) отличает константу от чтения чисел, но не ловит обнаруженную ошибку `*:0/2:30`.
- Новый тест flock проверяет реальную команду из `ExecStart`, причём и свободный, и занятый лок. Для заявленной защиты **cron ↔ timer** он содержателен. Защиту прямого ручного вызова он не проверяет — поэтому ложное обещание README остаётся незамеченным.

**Для штатного перехода с cron блокирующих незакрытых находок первого раунда больше нет.** Новые замечания относятся к документации ручного запуска и отображению нестандартного календаря; оснований объявлять сломанным штатный таймер нет.
