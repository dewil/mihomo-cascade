# Снимок состояния проверок каскада

## Проблема и границы

Повторный выбор первой ноды означает как ее доступность, так и отсутствие живых резервов. Существующая команда groups показывает глобальную историю выбранного proxy и не объясняет состояние конкретной проверки группы. За инцидент19.10 исторические результаты уже утрачены. Это диагностическое изменение: не менять fallback, endpoint, интервалы, группы, правила, установку служб или конфигурации.

## Контракт

REQ-HEALTH-01: `mihomo-api health` читает только GET /proxies один раз, без /delay, PUT или других изменяющих вызовов. Показывает все Fallback группы, их selected и каждого участника в заданном порядке. `mihomo-api health --json` дает один JSON объект со schema_version=1, observed_at UTC ISO8601 и groups массивом; каждый group содержит name, selected, status и members. Каждый member содержит name, status, checked_at и delay_ms. Только эти поля; не копировать API payload, endpoints, credentials, testUrl или connection metadata в вывод. Статусы member: up/down/unknown. Статус group: available/all_down/unknown; available если есть хоть один up, all_down только если непустой список и все down; иначе unknown. Выбранная нода сама по себе не является доказательством up.

REQ-HEALTH-02: здоровье определяется только extra[group.testUrl] с boolean alive и непустой корректной историей; отсутствие группы URL, участника, extra, валидного timestamp либо boolean => unknown. Global alive/history не заменяют per-URL состояние. Последняя валидная запись означает последний элемент массива (при поврежденном последнем элементе unknown, не искать старый успех). Timestamp timezone-aware, не более чем5сек в будущем и возраст <=90сек относительно observed_at. Старее => unknown. Unknown не считается down. delay0 разрешен для успешной проверки; для down delay_ms=null. checked_at выводить только для валидного timestamp; неизвестная задержка null. Отсутствующий/отрицательный/нечисловой delay не превращать в успех; bool не число. Ожидается integer delay>=0. Не сортировать priority members.

REQ-HEALTH-03: поврежденные group/member записи не роняют весь отчет и не создают фиктивное здоровье; глобально некорректный /proxies payload и ошибка транспорта дают ненулевой exit без сырого тела/секретов. Не менять поведение существующих conns/groups/delay кроме исправления help: delay активно запускает пробу и обновляет health-состояние, это не пассивное чтение.

REQ-HEALTH-04: text mode явно различает «доступен», «недоступен», «не определено», а для all_down поясняет, что выбранная первая нода не означает доступность. Не обещать подтвержденную причину инцидента. Документировать ограниченное окно истории, пассивность и freshness90сек (для fallback30сек), пример сохранения снимка оператором, отсутствие автоматической записи или фоновой службы.

## Приемка

Независимые тесты публичного CLI с локальным mock HTTP API, без чтения реализации: up/down/all_down/unknown, несовпадающие global/per-URL данные, stale/future/invalid timestamp, zero delay, missing member, secret sentinel not emitted, ровно один GET /proxies, JSON/text. Сначала RED на отсутствующей команде, затем поведенческие критерии GREEN. Реализация Astra, независимое ревью Haiku на финальном diff, полные существующие suites. Отдельный реальный изолированный Mihomo эксперимент normal/primary_down/all_down/recovery подтверждает механику, но не причину исторического отказа. Продовые ноды не отключать.
